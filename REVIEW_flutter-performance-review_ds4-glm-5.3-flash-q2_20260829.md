## Findings

- [medium] lib/data/database/app_database.dart:130-142 — migration step failure for a non-"already exists" error is logged then rethrown, but the `alreadyApplied` detection relies on string matching of the SQLite error message; a genuinely failed step that produces a different message (e.g. disk I/O error mid-`addColumn`) is rethrown correctly, yet a step that fails with a message containing "already exists" from a *different* cause (e.g. an index name collision from a prior partial run of a *different* migration) is silently swallowed and Drift advances `user_version`, permanently masking the missing column/index — every later query on that column then dies with "no such column" and the migration never re-runs — smallest safe fix: verify the failed statement's identity (e.g. check `PRAGMA table_info`/`sqlite_master` for the column/index before treating the error as benign) rather than matching the message substring.
- [medium] lib/data/database/app_database.dart:172-180 — the four `createIndex` migration steps are wrapped in `_step`, which swallows any error whose message contains "already exists"; if a prior partial upgrade created only *some* of the indexes and a later run re-executes `from < 6` for a user whose `from` is still < 6 (e.g. a downgrade-then-upgrade path), the swallowed duplicate-index error is benign, but a genuine failure (e.g. table missing because an earlier step was swallowed for the wrong reason) is also swallowed if its message happens to contain the substring, leaving the app to run full-table scans on `script_lines`, `scenes`, `recordings`, `cast_members` for every production-filtered query — consequence: per-production loads degrade to O(all rows) as productions accumulate — smallest safe fix: same identity-verification as above, or create the indexes idempotently via `CREATE INDEX IF NOT EXISTS` so the benign case needs no error-sniffing at all.
